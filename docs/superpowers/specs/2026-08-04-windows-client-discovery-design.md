# Windows 客户端发现与无弹窗诊断设计

## 背景

首个 Windows 验收构建能够安装、启动并通过 CI 冒烟测试，但真实机器上会周期性弹出终端窗口，且 League Client 诊断停留在 Demo。用户提供的日志只包含三次诊断系统初始化，没有客户端发现、候选路径或 LCU 连接结果。

当前实现通过 `wmic` 查询 `LeagueClientUx.exe`，通过 `reg.exe` 查询卸载注册表。隐藏窗口桌面程序启动这些控制台子进程时可能产生可见终端；`wmic` 也不是适合长期依赖的发现接口。发现流程没有结构化日志，因此失败后无法区分“进程未运行”“注册表无记录”“路径存在但 lockfile 缺失”和“lockfile 读取失败”。

## 目标

- 客户端探测期间不出现控制台或终端窗口。
- League Client 登录并进入主页后，应用能自动定位 `League of Legends/lockfile` 并连接 LCU。
- 自动发现失败时，用户可以选择 League 安装目录或 lockfile，选择结果在后续启动中复用。
- 日志记录每种发现来源的结果和 LCU 连接阶段，但不记录 lockfile 内容、LCU 密码、Authorization 或 Riot Token。
- Live Client 仍只在实际对局中连接；大厅阶段不把 2999 不可用误报为客户端发现失败。

## 非目标

- 不自动读取或展示用户的 lockfile 内容。
- 不改变 Arena 推荐、海克斯目录或出装算法。
- 不要求管理员权限，不扫描整个磁盘的所有目录。
- 不把 OP.GG MCP 是否连接作为 LCU 成功的前置条件。

## 方案选择

采用“原生 Windows 发现 + 有边界的路径候选 + 手动兜底”。

不继续以 `wmic` 作为主路径，因为它会触发当前的可见终端问题且在新 Windows 上可用性下降。单纯给 `wmic`/`reg.exe` 增加隐藏标志只作为低成本兼容兜底，不作为默认架构。只提供手动选择虽然可靠，但会破坏启动即用体验。

## 架构

### 1. 发现来源

`lcu/discovery.rs` 将发现拆成独立、可测试的来源，并按以下优先级合并候选：

1. 用户保存的 lockfile 路径。
2. `LEAGUE_CLIENT_LOCKFILE` 环境变量。
3. 运行中的 `LeagueClientUx.exe` 可执行文件目录。
4. Riot/League 卸载注册表的安装目录。
5. `C:\Riot Games`、Program Files 和各盘符根部的有限常见目录。

Windows 进程路径通过 Tool Help / Process API 枚举 PID，再用 `QueryFullProcessImageNameW` 获取，不启动控制台子进程。注册表通过 Windows Registry API 读取。若必须保留命令行兼容兜底，子进程必须带 `CREATE_NO_WINDOW`，并只记录退出类别。

候选路径在访问前规范化和去重。发现仅检查明确的候选 `lockfile`，不会递归扫描整盘。

### 2. 用户选择与持久化

新增 Tauri 命令在后端打开原生 Windows 文件夹/文件选择器，前端不获得任意文件系统读取权限。命令接收用户选择的 League 安装目录或 lockfile，并完成以下验证：

- 最终文件名必须为 `lockfile`；或选择目录下必须存在 `lockfile`。
- 文件必须是普通文件且当前进程可读。
- 内容必须符合 LCU lockfile 的五段格式，但验证结果不得把原文写入日志。

验证成功后，将路径保存到应用配置目录的专用 JSON 文件。健康面板在自动发现失败时提供“选择 League 目录”操作；保存后立即重试连接。配置无效时保留文件供诊断，但停止使用并提示重新选择。

### 3. 结构化诊断

每次发现周期生成一个关联 ID，记录：

- 发现来源（saved/env/process/registry/common）。
- 候选数量、路径是否存在、是否为文件、是否可读。
- 找到 lockfile 后的解析成功/失败类别。
- LCU 请求的阶段、HTTP 状态类别和重试结果。

日志中的路径仅保留盘符、来源和末级目录，用户名部分替换为占位符。密码、端口凭据、完整 lockfile、请求头和响应正文不得进入日志。重复的“未发现”结果按状态变化记录，避免每次轮询刷满日志。

### 4. 健康状态与界面

健康状态明确区分：

- `missing`：没有任何有效 lockfile。
- `degraded`：找到候选但不可读、格式无效或 LCU 暂时不可达。
- `ready`：LCU 已连接。

诊断界面为 `missing/degraded` 显示“重新检测”“选择 League 目录”和“导出诊断包”。导出成功后显示 ZIP 的实际保存路径，并提供复制路径按钮，避免只显示“已导出”却不知道文件在哪里。

Live Client 在大厅阶段保持 `unavailable` 说明，不升级为 LCU 故障。OP.GG MCP 保持独立可选状态。

## 数据流

1. 应用启动后加载保存路径并构造发现环境。
2. 后端依次执行各发现来源，合并并验证候选 lockfile。
3. 找到有效 lockfile 后解析内存中的 LCU 端口与凭据，建立本机 HTTPS 连接。
4. 后端返回脱敏的 session/health 快照；前端不接收原始 lockfile 或密码。
5. 自动发现失败时，用户选择路径；后端验证、保存并触发同一发现流程。
6. 每个关键状态变化写入滚动日志，导出时再次脱敏。

## 错误处理

- Windows API 权限不足或进程瞬间退出：跳过该进程，继续其他来源。
- 注册表键缺失：视为正常未命中，不弹错误框。
- lockfile 正在被 League 重写：短暂退避后重读，失败则返回 degraded。
- 保存路径移动或卸载：标记无效并继续自动发现，不阻止应用离线使用。
- LCU TLS/连接失败：记录错误类别，保留已发现路径，并允许重新检测。
- 所有发现错误与 Live Client 2999 错误隔离，任一来源失败不得终止应用。

## 测试

### Rust 单元测试

- 来源优先级、规范化、去重和有限候选范围。
- 保存路径、环境变量、进程、注册表和常见目录的命中/未命中。
- 无效文件名、不可读文件、错误 lockfile 格式和瞬时重写。
- 日志脱敏：用户名、LCU 密码、Authorization 和完整 lockfile 不出现。
- 状态变化去重，避免轮询日志洪泛。

### Windows 集成测试

- 模拟 League 安装在 C、D 和自定义带空格目录。
- 运行发现循环时断言没有可见控制台子窗口。
- 真实 League Client 打开后在限定时间内从 Demo 切换到 ready。
- 手动选择目录后立即连接，并在重启后复用。
- 大厅阶段 Live Client 不可用不影响 LCU ready。

### 前端测试

- missing/degraded 状态显示正确操作。
- 路径选择成功、取消和验证失败反馈。
- 导出诊断显示并可复制实际 ZIP 路径。

## 验收标准

1. Windows 10/11 上连续运行五分钟不出现任何 Terminal/Console 窗口。
2. League Client 已登录时，应用在十秒内从 Demo 切换为真实客户端状态。
3. 自动发现失败时，用户能通过选择目录完成连接且重启后仍有效。
4. 日志能说明每个发现来源为何命中或失败，并保持脱敏。
5. NSIS 与 Portable 构建、启动冒烟测试、前端测试和 Rust 测试全部通过。
